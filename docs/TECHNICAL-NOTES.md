# 설계하면서 고민한 점

## 실시간 상태와 영속 데이터의 분리

응시자의 현재 접속 상태나 진행 단계는 자주 바뀌고 빠른 조회가 필요합니다. 반면 답안과 로그는 처리 속도보다 누락 없이 남기는 것이 중요합니다.

실시간 조회 데이터는 Redis, 보존이 필요한 데이터는 PostgreSQL로 나눴습니다. 이 구분이 명확하지 않으면 Redis의 임시 데이터가 업무 기준값처럼 사용되거나, 반대로 단순 상태 조회까지 DB에 집중되는 문제가 생길 수 있습니다.

## API 요청과 저장 작업의 분리

답안, 로그, 상태 데이터를 요청마다 모두 직접 저장하면 응시 API의 응답 시간이 저장소 상태에 영향을 받습니다. API는 필요한 검증 후 이벤트를 발행하고, 워커가 이벤트 종류에 맞게 저장하도록 구성했습니다.

메시지 큐 사용만으로 유실 문제가 해결되는 것은 아니기 때문에 다음 항목을 함께 확인했습니다.

- 메시지 발행 실패 시 처리 경로
- 동일 이벤트가 다시 전달됐을 때의 중복 처리
- Redis 갱신과 DB 저장 순서
- 일부 저장만 성공했을 때 재처리 기준

## 인증 책임의 위치

서비스마다 JWT 검증을 따로 구현하면 제외 경로와 오류 응답이 달라질 수 있습니다. Gateway에서 공통 검증을 수행하고, 인증 서비스가 토큰 발급과 Redis 상태를 관리하도록 역할을 나눴습니다.

내부 서비스가 항상 Gateway를 통해 호출된다는 전제가 필요하므로, 직접 접근 경로와 운영 환경의 네트워크 정책도 함께 관리해야 합니다.

## 공통 모듈의 장점과 비용

공통 도메인 모듈을 사용하면 모델과 Repository 중복을 줄일 수 있지만, 필드 하나를 변경해도 여러 서비스의 버전을 함께 맞춰야 합니다.

변경 시에는 다음 순서로 확인했습니다.

1. 공통 모델과 Repository 수정
2. 공통 모듈 버전 변경
3. 사용하는 서비스의 의존성 업데이트
4. 직렬화 형식과 DB 컬럼 호환 확인
5. 관련 API와 워커 동작 확인
