# 실시간 평가 부하 시험 설계

실시간 평가에서는 단일 화면 응답시간보다 답안·상태 이벤트가 동시에 들어올 때 유실 없이 처리되는지가 더 중요했습니다. JMeter로 HTTP 흐름을 재현하고 Scouter에서 애플리케이션과 SQL 병목을 확인하는 방식으로 시험 항목을 구성했습니다.

## 대상 흐름

| 흐름 | 확인 항목 |
|---|---|
| 응시자 인증 | 토큰 발급·검증 지연, Redis 조회 실패 |
| 시험 진입 | 계획·응시자·문항 데이터 조회시간 |
| 답안 저장 | API 응답시간, 메시지 발행, 대체 저장 여부 |
| 상태 변경 | 중복 요청 처리, Redis와 DB 반영 순서 |
| 감독 이벤트 | 이벤트 증가 시 큐 적체와 워커 처리량 |
| 운영 조회 | 다수 응시자 상태를 조회할 때 응답 편차 |

## 측정 기준

- JMeter: 요청 수, 평균·최대 응답시간, 표준편차, 오류율, 처리량
- Scouter: 서비스별 응답시간, CPU, 메모리, SQL 시간, 외부 API 시간
- RabbitMQ: 대기 메시지 수와 소비 속도
- Redis: 명령 지연과 실패율
- PostgreSQL: 커넥션 사용량, 느린 쿼리, 저장 실패

HTTP 성공만으로 통과시키지 않고, 시험 종료 후 DB의 답안 수와 발생시킨 고유 이벤트 수를 대조합니다. 같은 이벤트를 다시 보낸 뒤 최종 상태가 한 번만 반영되는지도 확인합니다.

## 병목을 좁히는 순서

1. Gateway와 개별 서비스의 응답시간을 비교합니다.
2. API 응답은 빠르지만 반영이 늦으면 큐 대기량과 워커 처리량을 확인합니다.
3. 워커가 느리면 Redis와 DB 처리시간을 분리합니다.
4. DB가 느리면 이벤트별 쿼리 수, 인덱스, 커넥션 대기를 확인합니다.
5. 수정 후 동일한 데이터와 증가 패턴으로 다시 측정합니다.

보관된 자료에는 ClassRoom HTTP 시험의 실측 결과가 남아 있지만 실시간 MSA 운영 환경과 조건이 같지 않습니다. 따라서 이 저장소에는 해당 수치를 성능 결과로 옮기지 않고, 실제 구현 구조에 맞춘 재현 시나리오만 공개합니다.

[공개용 JMeter 계획](../samples/performance/realtime-event-scenario.jmx)은 내부 주소와 인증정보를 제거한 예제입니다.
